# ADR 0003: Identifiers, money, and time representation

- Status: Accepted
- Date: 2026-09-21

## Context

Identifiers, monetary values, and timestamps cross every domain and public
contract. Inconsistent choices here would undermine ordering, audit history,
financial correctness, and API compatibility.

## Decision

### Identifiers

- New persisted entities use UUID version 7 generated by the application.
- PostgreSQL stores identifiers in native `uuid` columns; APIs use the
  canonical lowercase hyphenated representation.
- Identifiers are opaque. No tenant, entity type, sequence, or sensitive data
  is encoded into an ID.
- Database uniqueness and idempotency constraints, not timestamp ordering in a
  UUID, prove uniqueness and processing safety.

### Money

- Represent money as a signed 64-bit integer minor-unit amount paired with an
  ISO 4217 currency code.
- PostgreSQL uses `bigint` for the amount and a constrained three-character
  currency column. Go uses an explicit value type rather than passing bare
  integers.
- HTTP and event contracts use an object such as
  `{ "amount_minor": 1050, "currency": "NGN" }`.
- Binary floating point is forbidden for monetary values. Currency exponent,
  allocation, and rounding rules must be explicit in the owning financial
  policy before calculations are implemented.

### Time

- Persist instants as PostgreSQL `timestamptz` and normalize them to UTC.
- APIs and events encode instants as RFC 3339 strings with sufficient
  fractional precision to round-trip the stored value.
- Calendar dates use PostgreSQL `date` and an explicit date type; they are not
  midnight timestamps.
- Domain behavior receives a clock at its application boundary. Tests do not
  depend on the process wall clock.
- Business timezone and business-date cutoff rules remain an explicit Phase 08
  product decision and must not be inferred from the host timezone.

## Alternatives considered

- Random UUIDv4 identifiers do not preserve insertion locality as well as
  UUIDv7.
- Database sequences are compact but are easy to enumerate in public APIs and
  complicate distributed creation and fixture isolation.
- Decimal database values are useful for rates and intermediate calculations,
  but stored money has a clearer exact invariant as integer minor units.
- Unix timestamps are compact but less self-describing and easier to interpret
  with the wrong unit.

## Consequences

All schemas and code must carry currency alongside amounts and reject invalid
codes or ranges at their boundaries. Historical timestamps are unambiguous,
while future business-date behavior remains policy-driven rather than coupled
to deployment location.
